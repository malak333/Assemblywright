# Developer Build Test and Phase Closeout

The accepted requirement is a usable, supervised Mac-to-Windows implementation and
validation loop. `DESIGN.md`, `docs/safety-rules.md`, and `docs/developer-build.md`
record the owner's deferred production-hardening scope. This phase preserves the
production schema and installed service. Its publication checkout excludes the
unfinished production control, VM, and active-executor drafts.

## Workflow and coverage matrix

The `unit-testing-test-generate` workflow was applied by inspecting state changes,
file operations, queue boundaries, and the Swift HTTP client, then adding focused
success, rejection, boundary, recovery, and error tests. The `e2e-testing` workflow
uses this product's native boundaries. There is no browser surface, so Playwright,
cross-browser matrices, and browser visual baselines are not applicable.

| Boundary | Cases | Test entry point |
| --- | --- | --- |
| Rust state | SQL write failure preserves memory state; failed Emergency/clear writes preserve the volatile latch; unconfirmed termination dominates cancellation; invalid/oversized requests; exact 100-feature capacity and duplicate replay; unauthorized mutation; emergency clear does not start | `cargo test -p assemblywright-master --bin assemblywright-developer` |
| Rust files | Local-only model URL admission; idempotent prepared edits; owner edit during generation; omitted existing files; relative paths; malformed/duplicate/empty/maximum change sets; context exclusions and budget | Same Rust unit suite |
| Swift client | Authenticated status; stale response after a command; rejected command; malformed/wrong-mode/unauthorized/offline response; invalid/missing configuration; observer cancellation | `swift test --disable-sandbox --package-path apps/mac --filter DeveloperRunnerClientTests` |
| Native HTTP/files/processes | Start/Stop/Emergency/clear/Resume; actual file writes and validation; paused checkpoint after restart; no rewrite or model recall on resume; auto-run on/off; malformed generation; failed validation and repair; fixed starting queue frontier | `python3 scripts/developer-runner-e2e.py --binary target/debug/assemblywright-developer` |
| Windows process lifetime | Validation parent and descendant exit after Stop, Emergency Pause, and abrupt runner death; paused applied checkpoint resumes after restart | Same native E2E, with Windows-only runner-crash scenario |
| Live Swift-to-Windows | Real app model reads and decodes the running Windows queue | Opt-in `DeveloperRunnerTests`, using `ASSEMBLYWRIGHT_DEVELOPER_LIVE_CONFIG` |
| Live local model | Three features generated by local Qwen and validated on Windows, with 10 then 20 then 20 tests passing | Earlier demonstration in `developer-build.md` |

The Swift transport fixture substitutes only HTTP delivery; it exercises the real
client model, decoding, state handling, and error reporting. The native E2E fixture
substitutes only the model response and uses real sockets, SQLite, files, commands,
and process lifecycle. Temporary test roots do not touch the owner's live queue.
Coverage is scenario-based; no numerical line/branch coverage percentage is claimed.
Launcher build/reconnect is exercised on the owner's actual SSH/model setup.

## CI and closeout evidence

`release-local.sh` runs Rust unit/integration tests and the full Swift package.
The master integration test `developer_workflow_e2e` invokes the native developer
E2E; the required Windows distributed workflow runs that same integration test
against its native `.exe` through `cargo test -p assemblywright-master`. No new
optional CI lane is needed. Both required hosted gates must pass before merge.

Documentation and knowledge-base updates accompany this phase. Independent review
found queue-frontier, interrupted-write, and validation-process lifecycle gaps;
the closeout addresses them with corresponding native tests. Final independent
review approved the phase with no remaining in-scope findings after rerunning the
strict Clippy command and whitespace check. Hosted gate results are recorded on
the publication pull request.

A second review added failure handling for process spawn cleanup/polling, a
volatile emergency latch that cannot be cleared by a failed SQLite write, and
local-only model URL validation. These are developer correctness fixes. The
review's proposed production append-only audit and automatic log-redaction layer
were not adopted: the accepted developer scope intentionally retains owner-local
validation logs and a durable current-state snapshot. Those production controls
remain deferred by the owner's instruction; logs are not published by the app.

The isolated phase passed 13 Rust unit tests on Mac, 14 on Windows (including
a real kernel-query failure), and the native process E2E on both hosts. The Windows E2E verified the validation parent and descendant
exited after abrupt runner death; the reported Stop time was under 0.2 seconds.
Six deterministic Swift client tests (including four error-response cases) passed,
and the full Swift package passed 205 tests across seven suites, with the opt-in
live test skipped when no connection configuration was supplied. Both hosts passed
strict Clippy for the developer binary. Final whole-repository and hosted results
are tracked separately from these focused checks.

The earlier broad local run was interrupted by macOS test startup delays. That
partial run is not a full gate pass. Native visual UI automation also failed when

UI test. Signed installation, protected production execution, and automatic GitHub

## Project chat, planning, review, and escalation continuation

The continuation applies the same unit workflow to exact chat/model attribution,
planning state transitions, attachment bounds, review bindings, proposal lifecycle,
cumulative baselines, cancellation, stale bytes, migration, and recovery. Its native
E2E uses Rust/Swift clients, loopback HTTP, real files, Windows processes, SQLite,
and fixture model/reviewer subprocesses. The `developer_workflow_e2e` Cargo wrapper
runs all seven scripts on both required CI hosts. Browser E2E and cross-browser
matrices do not apply because the owner surface is a native Swift application.

Historical focused runs before the 12:50-12:56 owner interaction passed 41 Rust tests,
244 Swift tests, and seven Windows developer process E2Es. The current isolated
candidate separately passed 44 Rust tests on Mac, the same 44 tests on native
Windows, 235 Swift tests, strict developer Clippy, and all seven native Windows
process E2Es. The Cargo wrapper also ran all seven process E2Es locally, including
new validation-failure and reviewer-rejection cases that preserve the auto-run
frontier across restart. The owner screenshots then
confirmed the repaired sheet's pinned Close and action buttons. The owner applied
proposal 4, but its 24-test validation failed two tests: a hidden/unrealized Tk
window height assertion observed height 1, and a shallow/brittle widget-tree search
could not find the nested Input card. Codex review did not run and the feature did
not advance. These failures are current acceptance evidence and keep the GUI feature
open; earlier focused passes do not override them. This is owner-observed native UI
evidence, not machine-automated screenshot regression coverage.

The continuation also covers two fail-closed recovery regressions. If committing an
Emergency Pause fails, the runner retains its volatile emergency latch and rejects
new work rather than presenting a durable acknowledgement. Completed chat and
planning provider responses are retained in memory when their completion write
fails. While that runner process remains alive, status GET polling exposes
`recovery_pending` or `planning_recovery_pending` and retries the exact completion
without reexecuting the provider. A process restart cannot recover that in-memory
response: startup records the pending chat or planning call as interrupted and a
new owner retry may call the provider again.
